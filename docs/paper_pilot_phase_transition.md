# PaperPilot runtime phase transition

This workflow moves a quiescent PaperPilot run to a new reviewed runtime without editing its historical `OPEN`, checkpoint events, application journal, or model budget. The new runtime creates its own `OPEN` and an `IMPORT_PHASE` event that reference a pinned capsule. The application retains the historical archive for audit. No transition step calls a model, prepares a source, or publishes a graph assertion.

The embedding application supplies the old and new PaperPilot construction arguments, enrolled reviewer trust, current access policy, source-open approval, and an externally approved transition request. These modules do not create signers or grant broad ACL access.

## Required sequence

1. Quiesce the application and establish sole ownership of the historical pilot, controller, graph backend, budget, and application journal. Verify the old implementation identity and that no SQLite transaction or provider process remains active. Classify the external semantic attempt inventory; an absent raw output alone is not proof that a provider was never called. Resolve any unknown attempt before allowing a later model execution.
2. Under the genuine old package, load `src/paper_pilot_phase_export.py` as a source-checkout helper. `export_phase` uses the already opened old Pilot and journal. Supply the exact expected old implementation identity, signed source-open digest, external semantic intent and complete five-file attempt manifest. It takes online backups of all four stores, verifies the logical schema and rows before and after, and publishes a capsule. A retry uses the same destination and exact old state; conflicting prior bytes stop the transition.
3. Close every old Pilot, backend, budget, journal, and controller handle. On Windows, call `src/paper_pilot_phase_cutover.py` with the fixed old state path, a disjoint archive path, the five expected file hashes, and the application owner's SID. It denies creation beneath the old namespace, renames the closed state directory, and seals a fence receipt. When the old controller lock must remain held until new opens are denied, use the separately reviewed `src/paper_pilot_phase_cutover_guarded_v2.py` admission handoff described below. A crash before the rename leaves the new phase inactive. A crash after the rename requires exact fence reconciliation. Do not activate a target while the old namespace can still be opened for writing.
4. Under the new reviewed package, create `PhaseAuthority` with an exact signed layout binding: capsule, old and archived paths, fence, common lock, implementation identity, run ID, epoch, authorization, and activation pointer. `restore_target` validates the immutable capsule and four backups, restores graph and budget into a new inactive target, and writes persistent phase bindings. It never resets the old model reservation. Checkpoint and application journal are created by the new Pilot and controller; they import the old chains by reference.
5. Construct the new backend, budget, Pilot, and controller with that authority and the **same application run/config identity**. Import the capsule using the enrolled signed `PHASE_IMPORT` authorization. Verify exact old request results, blobs, source receipts, graph/source status, budget, and journal linkage. Complete interrupted controller `FREEZE` to `APPLICATION_PHASE_IMPORT` by same-request reconciliation.
6. Only after complete readback, issue the separately reviewed `PHASE_ACTIVATE` authorization and call `activate_imported_phase`. It publishes the active pointer once. Identical replay is read-only; conflicting activation is rejected. Reopen with the same phase layout and verify current pointer, signer revocation, archive fence and bytes, graph, budget, and imported history before further stage actions.

The Windows namespace fence limits cooperative, unchanged old launchers. It is not a security boundary against a malicious process holding the same owner credentials. All supported new Pilot, controller, backend, and budget writes require the shared phase authority. Unmanaged direct SQLite mutation is outside this API contract and must be excluded by application ownership and operational access controls.

The guarded admission handoff requires an independently established sole owner before its first ACL change. It holds the two existing stage byte locks and the old controller byte lock, pins the original five file bytes and Windows DACLs, then denies new write and append opens on those files. It rejects any original deny rule for the owner SID, because removing its added rule after the rename would otherwise remove unrelated owner denies. It checks that the old parent DACL gains only its deny-create rule, closes the controller handle, and renames on the same volume while the stage locks remain held. The fixed old parent stays fenced; the archived files regain their original effective access rules. A durable admission receipt permits exact-input recovery after an interrupted ACL update or rename. A partially installed barrier is a hold until the same reviewed request reconciles. Neither an ACL receipt nor a file lock alone proves that all old launch authority was excluded before the first ACL update; the embedding application must provide that separate evidence. The helper refuses non-Windows execution.

Windows may serialize the owner SID in a DACL string as an SDDL alias: the Users group `S-1-5-32-545` is `BU`, and a machine's built-in Administrator (RID 500) is `LA`, which is the identity of a hosted Windows runner. The v1 fence, the guarded v4 fence, and `PhaseAuthority.verify_fence` therefore recognize their exact deny-create and per-file deny ACEs through `trace_gc.phase_authority.canonical_dacl_trustee` and its ACE helpers instead of a literal numeric-SID substring. The helper asks the local Windows security-descriptor conversion how it would spell the receipt's numeric SID, so an alias is never mapped back to a caller-selected numeric SID, and distinct account or domain SIDs that share RID 500 stay distinct. Only the trustee field is normalized: ACE type, flags, rights, object fields, order and the extra-ACE check still compare exactly, `directory_dacl_sddl` serialization is unchanged, and receipts keep the numeric `deny_sid` and the digest of the raw, un-normalized SDDL. Alias spelling is machine-specific, so a receipt is validated against the DACL text and serialization of the machine that validates it; the raw-SDDL digest pin still ties a receipt to the DACL spelling it recorded. Off Windows the alias relation cannot be established: a numeric SID fails closed with `PHASE_PLATFORM`, and non-numeric trustee text passes through without mapping. Because this changes the packaged `trace_gc/phase_authority.py`, the implementation identity (`trace_gc.paper_pilot.implementation_identity`) and every binding derived from it change; a private plan or phase binding pinned to the previous identity must be newly bound and reviewed, and an expired private window is not reopened by this public change.

The v1 fence publishes its receipt only if the parent deny really refuses the process that is running it. After the pinned inventory check and after the exact `(D;;LC;;;sid)` deny is present (installed by the call if absent), the helper creates one uniquely named `.fence-probe-<hex>` directory directly beneath the actual fenced parent `old.parent`, with the current process's own token, and removes it again. Only a Windows error 5 (`ERROR_ACCESS_DENIED`) counts as a refusal; a creation that succeeds, any other error, or a probe directory that cannot be removed holds with `PHASE_FENCE`. The probe samples the fenced parent itself, not the receipt's control directory, whose filesystem, DACL, control flags and owner may differ. A hold leaves the old state, the archive path and the receipt exactly as they were; a deny this call added is removed with `icacls /remove:d` and the parent DACL is read back equal to its pre-call text, otherwise the hold says the added deny could not be removed and verified (re-running the same call is safe, and an interrupted call leaves the same recoverable state as an interrupted rename: deny present, old state in place). A replay never removes a deny it did not add. An old parent that already carries a different deny for the fence SID holds before any ACL change. The temporary deny on `old.parent` is a reversible effect, not zero effect. Hosted runs showed the full original process token creating a directory beneath such a deny while a privilege-stripped copy was refused; the reason is not established here and the gate names no privilege. The guarded v2 helper is unchanged, and v4 keeps its existing parent-deny property without this gate.

`src/paper_pilot_phase_cutover_guarded_v4.py` adds an optional application observer to the continuous-lock transaction. After the source-stage, phase-stage, and controller locks and pinned old file/ACL checks, but before the quiescence receipt or first ACL update, the helper calls `observer(old_root=..., archived_root=..., source_handle=..., phase_handle=..., controller_handle=..., writable_database_names=...)`. The sorted database-name tuple identifies the four stores still lacking the durable per-file deny; a replay observer can retain read handles for just those stores. The observer returns a context manager holding any approved read leases. Its lease remains open through readback of the five per-file write denies and the old-parent deny, then closes before the same-volume rename while the two stage locks stay held. Rejection creates no quiescence or barrier receipt and changes no ACL. A barrier-only or partial-deny replay requires a fresh observer under the stage locks; `controller_handle` is `None` if the controller file already has the durable deny. The application must independently bind the observer code, current process census, and signed stage approvals. The generic helper does not determine sole ownership from a caller-supplied receipt.

## Recovery and evidence

- Export and restore use deterministic `.pending` SQLite backups. Completed pending backups can be promoted after logical readback; incomplete pending bytes are preserved as `.failed.*` before another backup is taken. Unknown destination files or changed old state cause a hold.
- Restore readback of a quiescent WAL-mode graph or budget store opens the main database with SQLite `mode=ro&immutable=1`. It rejects any preexisting `-wal` or `-shm` file and checks again after the connection closes. Ordinary `mode=ro` can create those sidecars on Windows; an interruption after that readback would otherwise make an identical restore request reject its own target inventory. A real nonempty WAL or unexpected SHM is a hold, including a zero-byte WAL left by an older reader. The restore does not delete sidecars or infer that a live writer is absent from file size alone.
- A target previously restored by a runtime with the sidecar defect needs separate, reviewed recovery. Preserve its main databases, receipt, WAL/SHM files and hashes; establish ownership and classify the sidecars before any approved reconciliation. This code change alters the PaperPilot implementation identity, so old phase authorizations and activation bindings cannot be reused with a new runtime. Never hotpatch the active phase or remove historical sidecars as part of this fix.
- SQLite documents that read-only WAL access can create `-wal`/`-shm` files and that `immutable=1` skips locking and change detection ([WAL](https://www.sqlite.org/wal.html), [WAL format](https://www.sqlite.org/walformat.html), [URI filenames](https://www.sqlite.org/uri.html)). The immutable read in this helper applies only to a closed restored store under the phase staging authority; it must never be used as a general live-database read path.
- The old capsule, original four-store backups, historical checkpoint and application events, model reservation, external attempt manifest, and any failure artifacts remain available. The phase pointer does not rewrite those records.
- A signed release must pin the final reviewed old and new implementation identities, capsule, source-open approval, attempt manifest, fence, target layout, and activation bytes. A passing authored fixture is mechanical evidence only; it is not approval to transition a live run or to execute a model.
- The new runtime changes the code identity. Recheck any code-closure source gate and preregistered empirical controls affected by that change before the first new phase action. Do not reuse an old receipt as approval for new code.

Use isolated task or temporary directories for authored fixtures. `tests/test_paper_pilot_phase_backup.py` exercises pending backup reconciliation and schema-object hashes without source PDFs or providers; `tests/test_paper_pilot_phase_fence.py` exercises an owned disposable Windows namespace fence. `tests/test_paper_pilot_phase_cutover_guarded_v2.py` exercises the guarded handoff, crash replay, owner deny preservation, parent ACL drift rejection, and a new budget constructor blocked during the close-to-rename gap. `tests/test_paper_pilot_phase_cutover_guarded_v4.py` covers the held observer interval, rejection before effects, and barrier-only/partial-deny replay. `tests/test_paper_pilot_phase_trustees_v1_v4.py` runs the v1 and v4 fences, the real `PhaseAuthority` constructor over a signed activation pointer (current, fenced-but-inactive, tampered and lock-contention cases through `write()`, `staging()` and `RunBudget`, with the owned database unchanged after every rejection) and the packaged receipt validator against real Windows-spelled DACLs (the Users alias `BU`, the machine RID-500 account and the runner's own identity). It covers replay, crash recovery, existing-deny rejection, live denied opens, and rejection of a distinct RID-500 SID, other trustees, masks, flags, ACE types and changed digests; it needs native Windows. The one fabricated foreign-RID-500 deny (a full SID no account database knows, so `icacls` cannot install it) is installed through `tools/windows_native_acl.py`, which parses SDDL with the numeric SID and writes the descriptor with `SetNamedSecurityInfoW`; the test then asserts the exact stored ACE list, count, type, flags, rights, trustee, owner and digest and removes the ACE with verification. The live recreation-denial assertions (`mkdir` on the closed old path) call `require_recreation_denied`, which attempts creation with a privilege-stripped token and the full original token by `os.mkdir` and `CreateDirectoryW`, runs an `AccessCheck`, lists the enabled privileges and labels the result. Only `DENIED` passes: creation by either route with the full original token is a failure whatever the privileges, `AccessCheck` or the stripped token report, and a refusal counts only when every route and token fails with `ERROR_ACCESS_DENIED` (5); a missing parent, an existing target, an invalid path, a resource error or an outcome with no Windows error is `REFUSED_WITHOUT_ACCESS_DENIED`, which also fails, and the probe must verifiably remove anything it created. The labels `FULL_TOKEN_CREATES_WHILE_BYPASS_PRIVILEGE_ENABLED` (an enabled `SeBackupPrivilege`/`SeRestorePrivilege` coincides with a creation the DACL check would refuse), `FULL_TOKEN_CREATES_UNEXPLAINED`, `DACL_GRANTS_ADD_SUBDIRECTORY` and `KERNEL_CREATE_IGNORES_DACL` are observations that fail with the sanitized report; none asserts a proven cause and every report carries `cause_established: false`. The cause of hosted runs that created the closed path despite a first `(D;;LC;;;sid)` parent ACE is not established by Linux or model evidence; the hosted `tools/windows_native_acl.py` diagnostics step and the probe report are what can establish it. Removing a descriptor-installed deny, and verifying any restoration, compares trustees by full numeric SID after the operating system's own spelling (so a deny Windows reads back as `LA` or `BU` is found, while a distinct domain RID-500 SID is never collapsed into it), keeps every other ACE in order, and verifies the DACL control and protection flags and the owner; a drift is reported as a failed cleanup, never hidden. `tests/test_windows_native_acl.py` covers these helpers (portable cases against a labelled fake of the Win32 layer, native cases on Windows). `tests/test_paper_pilot_phase_trustees_model.py` runs the same fence and phase code on every platform against a labelled model of the Windows DACL, `icacls` and SID-spelling seams, plus the exact ACE count, order, flag and rights contract (an explicit copy of an inherited ACE is never tolerated) and the off-Windows contract; it is not native Windows evidence. `tools/installed_phase_authority_check.py` runs from the installed wheel in a directory outside the checkout against declared source digests: portable provenance and off-Windows checks everywhere, and the native real-constructor and trustee checks on Windows only (35 checks, including the foreign-domain RID-500 deny installed and removed by numeric descriptor operations through the source-only `tools/windows_native_acl.py`, loaded by path without touching `sys.path` and with every `trace_gc` module still verified as the installed package), reporting `native_windows` as `RUN` or `NOT_RUN`. The real old-runtime export and new-runtime import must be reviewed against pinned application inputs before execution.

The native helper `tools/windows_native_acl.py` also runs as a standalone script (`python tools/windows_native_acl.py`, optionally `--stages-only`); it inserts the checkout root on `sys.path` only for that script entry, never when it is loaded by path, and `SourceScriptTests` run it in a fresh interpreter from another directory. Its report names the completed stages and carries no path, account or machine SID. `installed_exactly` is the conjunction of per-component facts (DACL control and protection flags, the ordered ACEs with unexpected and missing ones, explicit and inherited tallies, and the owner), so a failed installation prints which component differed; the diagnostics install on an owned fixture stabilized before any pin. The restricted-primary child launcher runs the child in an owned kill-on-close job object: it distinguishes `WAIT_TIMEOUT` from `WAIT_FAILED`, terminates the job (falling back to the process) on timeout or failure, waits again, terminates a child whose assignment to the job failed directly with `TerminateProcess` (ending an empty job stops nothing outside it) and accepts that stop only when the final wait sees it signaled, never treats `STILL_ACTIVE` as an exit code, counts the job's remaining processes (a surviving descendant is terminated and the run is not `completed`), and keeps its handles when cleanup cannot be shown. A launch is accepted only when `launch_defects` is empty, which requires `completed` and `cleanup_verified`, no retained handles, a verified privilege restoration and no recorded error; the exit code alone is never acceptance. The one disabled privilege the launcher may enable (`SeIncreaseQuotaPrivilege`, only after Windows refuses with `ERROR_PRIVILEGE_NOT_HELD`) is restored to its captured attributes and the whole process-token inventory is read back, a mismatch being a cleanup failure. The launch report's `child_stopped` is true only when nothing was started or the process was seen signaled and the job is empty (a handle that will not close does not change it); fixture restoration and removal depend on it, not on handle or privilege cleanup: when it is not established, or the launcher raises, the standalone section leaves the child's fixture and its DACL as they are, reports `fixture_retained`, keeps the temporary root in place (the run is not clean) and relies on the kill-on-close job handle it still owns for bounded teardown. The test-suite launcher consumers follow the same rule through `ChildStopHold`: the native helper cases and the strict-producer child case in `test_paper_pilot_phase_trustees_v1_v4.py` launch through it, and a launch that is not shown stopped, or a launcher that raises, makes their teardown restore no ACL, remove nothing, detach the temporary directory's own finalizer and fail loudly, while a stopped child or a launch that failed before creating any process still restores and removes the fixture. This is a static caller contract; no orphaned Windows child or deletion race was observed. The standalone `restricted_primary_child` section separates `restoration_verified` (the fixture and this process's own probes) from `evidence_complete` (the child launched, finished in time, left nothing behind and wrote a complete report object with a known verdict and every required field); a missing, malformed, `null`, non-object, error or incomplete report is listed in `not_run`, whatever the parse returned. The standalone `installation_observation` section keeps an installation that reads back inexactly apart from a restoration that cannot be shown: only the stabilized installation gates `stabilized_install_and_restoration_exact` (the two unprotected shapes are diagnostics), while `restoration_verified` is true only when every fixture whose original descriptor was captured shows a verified restoration, an unverified or raised restoration is listed in `restoration_unverified`, and `main()` is clean only with both. The standalone `main()` is exercised at runtime with the section producers replaced: its exit code and the report's `cleanup_verified` follow that section (and each earlier section), and a producer error is recorded and fails the run. Native positive coverage and the original-token refusal are two reported gates: `JRAPHYTE_SUPPORTED_CONTEXT=required` makes the producer, receipt, constructor and current-write cases run the supported branch and fail where the context is unsupported, the strict wrapper test runs that branch inside a restricted-primary child whose own process token is the one under test, and `JRAPHYTE_BRANCH_LOG` records which branch each case took. A green run that took only the refusal branch is negative evidence and is not positive qualification. None of these diagnostics establishes a cause.

## What each distribution ships

The source ZIP from `tools/package_project.py` carries the public source files that the packager's current suffix and exclusion policy selects (it still excludes, for example, the tracked `docs/workflow/render.mjs`, private inputs, models and outputs), under a root directory prefix, plus `MANIFEST.json`; it is not a copy of the whole Git tree. The sdist carries `trace_gc`, `pyproject.toml`, `MANIFEST.in`, the licence and README, and, through explicit `MANIFEST.in` rules rather than a build-backend default, the phase and Windows test modules (`tests/test_paper_pilot_phase_*.py`, `tests/test_windows_*.py`, `tests/test_sdist_phase_distribution.py`) with the helpers they import or load by path (`tests/phase_trustee_harness.py`, the `src/` modules `paper_pilot_phase_cutover`, `_cutover_guarded_v2`, `_cutover_guarded_v4` and `paper_pilot_phase_export`, and `tools/installed_phase_authority_check.py`, `tools/windows_fence_diagnostics.py`, `tools/windows_fixture_acl.py`, `tools/windows_native_acl.py`, `tools/sdist_discovery.py`, `tests/test_sdist_discovery.py` and `.github/workflows/test.yml`). The declared build backend (`setuptools>=68`; 68.0.0 and 84.0.0 were exercised) already adds `tests/test*.py` by default, so the three test rules pin that behaviour rather than depend on it, while the helper rules are what the old sdist lacked. `tests/test_sdist_phase_distribution.py` builds a real sdist with the installed backend, requires every file the affected tests need to be a member, and requires every affected test module to import from the extraction; a missing module fails and nothing is skipped. The workflow does not assume a spelling of the archive: setuptools 68 writes `trace-gc-0.4.0.tar.gz` with root `trace-gc-0.4.0` and setuptools 84 writes `trace_gc-0.4.0.tar.gz`. `tools/sdist_discovery.py` requires exactly one archive (and one wheel), checks the project name, extracts with member-name checks and returns the single top-level directory, and fails on zero or several candidates; `tests/test_sdist_discovery.py` covers both spellings, the negatives and the real workflow step. The wheel installs only `trace_gc`, so it has no `src/`, `tools/` or `tests/`; the installed-wheel check runs the tool from the extracted sdist against the installed package. Linux and model runs of these distributions are not native Windows evidence: the native v1, v4, constructor, staging and installed-wheel checks run in the hosted Windows job and are NOT_RUN on Linux.
